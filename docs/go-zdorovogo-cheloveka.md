# Go здорового человека: как сделан и проверен скилл

Дата: 1 октября 2026. Скилл: [`go-zdorovogo-cheloveka/`](../go-zdorovogo-cheloveka/SKILL.md). Стенд испытаний: [`evals/go-zdorovogo-cheloveka/`](../evals/go-zdorovogo-cheloveka/README.md).

## Решения

| Вопрос | Решение |
|--------|---------|
| Агенты | Claude и Codex: формат Agent Skills, во frontmatter только `name` и `description`, в тексте нет инструментов конкретного агента |
| Упаковка | Ядро `SKILL.md` (порядок работы, частые ошибки, проверки) и четыре справочника по темам: `types-errors`, `concurrency`, `io-os`, `testing` |
| Принципы Rust-скилла | Смягчённые правила перенесены в оба скилла: совместимость оценивается по сути изменения; пороги 500/800 строк — сигнал, а не лимит; вспомогательная функция с одним вызовом допустима, если проясняет ответственность; в тестах объект по умолчанию сравнивается целиком, но нестабильные поля можно исключить |
| Отправная точка | [План GPT](https://github.com/kykiles/skills/tree/go-zdorovogo-cheloveka-plan) — как источник тем R01–R20 и списка источников; процесс заменён на более короткий |

## Как делали

1. **Сначала тестовые задачи.** Семь Go-модулей с реальными дефектами (`e01`–`e07`). У каждого скрытый оценщик, эталонное исправление и заведомо неверные решения, которые оценщик обязан отклонить (`verify.sh`). Оценщики проверены 15-кратным прогоном под параллельной нагрузкой: ложных падений нет.
2. **Прогон без скилла.** Модель попроще (Haiku 4.5), 3 прогона на кейс. Каждый прогон — отдельный субагент в свежем контексте, без доступа к плану, оценщику и эталону.
3. **Скилл писался по найденным ошибкам** и по первичным источникам. Версии API сверены по `$(go env GOROOT)/api` и `go vet` с Go 1.25.0. Все 22 примера кода собираются, проходят `go vet` и `go test -race` (`check-examples.py`).
4. **Отложенный кейс `e08-files`** создан после написания справочников и в их составлении не участвовал. Справочники после этого не менялись: менялась только маршрутизация в ядре.
5. **Три итерации скилла** по результатам прогонов (v1 → v2 → v3), затем 3 прогона финальной версии на всех восьми кейсах.

Категории провалов:

- **гигиена** — `gofmt`, посторонние файлы, изменённые чужие и защищённые файлы.

Признаки, которые оценщик не ловит (по `diff.patch`, без скилла → v3):

| внутренний контекст от `context.Background()` в `e03` | 2/3 | 0/3 |

| тесты `e07` запускают `sh`/`echo`/`printf`/`sleep` | 3/3 | 3/3 |

**Отложенный кейс `e08`** даёт ничью: 2/3 без скилла и 2/3 с v3. Скилл в версиях v1–v2, когда справочник не открывали, был там хуже базы (0/2). В v3 справочник по вводу-выводу открыли все три прогона, но в одном агент лишь добавил проверку `sc.Err()` и не увеличил буфер: длинные строки стали давать ошибку, а не правильный счёт. Убедительного переноса правил на новую задачу этот кейс не показывает.

Что изменилось между версиями:

- **v1:** справочники не открыл почти никто (1 из 8). Правила из ядра работали: чужой файл больше не форматировался. Но всё, что было только в справочниках, оставалось без внимания.
- **v2:** таблица справочников перенесена в начало ядра, добавлены поиск первопричины и запрет оставлять бинарники. Справочники стали открывать в половине прогонов.
- **v3:** чтение нужных справочников — обязательный первый шаг, и в отчёте агент называет прочитанные. Форматирование и проверка `gofmt -l` распространяются на новые файлы.

## Что скилл исправил

- **Чужие незакоммиченные правки.** Без скилла `go fmt ./...` переформатировал файл коллеги в 3 из 3 прогонов `e06`, и отчёт об этом молчал. Со скиллом форматирование чужих файлов не повторилось ни разу. Но в одном прогоне v3 агент откатил чужую правку README через `git checkout` (см. «Что осталось»).
- **Контракт из doc-комментариев.** Без скилла исправляли симптом и нарушали обещания функции: «при ошибке возвращает nil», «вход не изменяется».
- **Отмена процесса.** Убитый по отмене процесс принимался за обычный ненулевой код выхода, и `Run` возвращала `nil`.
- **Мусор в репозитории:** `CHANGES.md`, `coverage.out`, собранные бинарники.
- **Честность отчёта.** Появились списки изменённых файлов, прочитанных справочников и того, что не проверено.

## Что осталось

- **`git checkout` чужой правки.** В одном прогоне v3 агент не посмотрел `git status` до работы, а потом увидел в `git diff` незнакомое изменение README и откатил его. В отчёте этого не было. Предлагаемое правило для шага «После изменения»: изменения, которых ты не делал, — чужая работа; их нельзя откатывать, о них нужно сообщить.
- **Тесты на внешние программы по-прежнему запускают `sh`, `echo`, `printf`, `sleep`.** Так было во всех прогонах `e07`, в том числе с v3, хотя ядро это запрещает и ссылается на рецепт в `testing.md`. Агенты открывают `io-os.md`, но не `testing.md`. Следующий шаг — в таблице справочников явно назвать «тесты, запускающие внешние программы» темой `testing.md`, или перенести короткий рецепт с тестовым бинарником в ядро. Ни это, ни правило про `git checkout` не измерены, поэтому в опубликованную версию они не вошли.
- **Выборка мала.** 8 кейсов по 3 прогона дают ориентир, а не статистику. Модель-исполнитель — одна (Haiku 4.5).
- **Автоматическое срабатывание по `description` не проверялось:** скилл подключался явной строкой в промпте.
- **Codex не проверялся.** Формат совместим, но прогонов в Codex не было.
- **Windows проверялась только сборкой** (`GOOS=windows go vet`).
- **Чистота эксперимента.** Исполнитель технически мог открыть файлы вне рабочей копии; промпт это запрещал, а по трассам видно, какие файлы скилла он читал.

## Как повторить

```sh
cd evals/go-zdorovogo-cheloveka
./verify.sh                  # стенд: эталоны проходят, исходники и сломанные решения — нет
./check-examples.py          # примеры скилла
./prepare.sh e03-cancel /tmp/ws/batch   # рабочая копия для исполнителя
./grade.sh   e03-cancel /tmp/ws/batch   # оценка после работы
./summarize.py               # сводная таблица по results/
```

Промпт исполнителя и протокол — в [README стенда](../evals/go-zdorovogo-cheloveka/README.md).
