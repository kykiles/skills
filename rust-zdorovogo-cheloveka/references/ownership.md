# Владение: строки, срезы, клонирование, итераторы, времена жизни

Правила описывают причину выбора, а не вводят запрет на одну из конструкций. Сначала проверь контракт функции, владение данными и поведение при ошибке; затем выбери самый ясный вариант, который решает текущую задачу.

## `&str` или `String`

**Принцип:** принимай `&str`, когда функции достаточно прочитать текст во время вызова. Принимай или возвращай `String`, когда результат должен владеть текстом: хранить его после вызова, менять или передать владение дальше. Если функция действительно забирает строку, принимай `String`, чтобы вызывающий код мог передать готовое значение без скрытого клонирования.

```rust
// Только чтение: подойдут и строковый литерал, и String.
fn is_user_name(name: &str) -> bool {
    name.starts_with("user_")
}

// Хранение: User должен владеть именем после завершения вызова.
struct User {
    name: String,
}

impl User {
    fn new(name: String) -> Self {
        Self { name }
    }
}
```

**Проверка выбора:** если заменить `String` в `User` на `&str`, появится зависимость времени жизни `User` от входной строки. Она оправданна, только когда такое заимствование действительно задумано. Если заменить параметр `is_user_name` на `String`, простой вызов начнёт требовать передачи владения или ненужного выделения памяти. При создании нового текста, например после `to_uppercase()`, возвращай `String`; ссылку на локально созданную строку возвращать нельзя.

## Срезы вместо ссылок на владеющие контейнеры

**Принцип:** для чтения принимай `&[T]` вместо `&Vec<T>`, `&str` вместо `&String`, `&T` вместо `&Box<T>`, `&Path` вместо `&PathBuf`. Срез принимает больше вариантов (массив, часть вектора, литерал) и не раскрывает, как вызывающий хранит данные. `&mut Vec<T>` оправдан, только если функция меняет длину (`push`, `retain`); для изменения элементов достаточно `&mut [T]`.

```rust
fn total_len(names: &[String]) -> usize {
    names.iter().map(String::len).sum()
}
```

**Проверка выбора:** если функция вызывает у `&Vec<T>` только методы среза (`iter`, `len`, индексацию), замени тип на `&[T]` — вызовы с `&vec` продолжат компилироваться благодаря deref-приведению. Clippy отмечает это как `ptr_arg`. В публичном API такая замена меняет сигнатуру, поэтому делай её только в рамках задачи.

## `clone()` или заимствование/перемещение

**Принцип:** сначала выясни, кому требуется владение. Заимствуй для временного чтения, перемещай значение, если прежнему владельцу оно больше не нужно. Клонируй осознанно, если нужны два независимых значения или если это делает простой участок кода заметно понятнее и стоимость приемлема. Не добавляй `clone()` лишь затем, чтобы подавить ошибку borrow checker, не разобравшись в причине.

```rust
// После чтения строку можно передать в хранилище без копии.
fn keep_name(name: String, names: &mut Vec<String>) {
    println!("{name}");
    names.push(name);
}

// Оба хранилища должны независимо владеть своим экземпляром строки.
fn keep_in_both(name: String, active: &mut Vec<String>, history: &mut Vec<String>) {
    history.push(name.clone());
    active.push(name);
}
```

**Проверка выбора:** удали `clone()` мысленно: если исходное значение можно передать на последнем использовании, копия лишняя; если оба получателя должны хранить независимые строки, она обоснованна. Учитывай конкретный тип: `String::clone()` копирует содержимое, а `Arc::clone()` создаёт ещё один указатель на те же данные с увеличением счётчика ссылок; `Clone` сам по себе не обещает ни дешёвую, ни глубокую копию. Не усложняй архитектуру только ради устранения одной дешёвой и понятной копии.

## Цикл или цепочка итераторов

**Принцип:** применяй итераторы, если последовательность преобразований читается как описание результата. Пиши явный `for`, когда в теле несколько действий, побочные эффекты, `break`/`continue` или ранняя передача ошибки и цепочка методов затрудняет понимание. Цикл `for` тоже работает через итератор; выбирать между ними по одному лишь предположению о скорости не следует.

```rust
// Линейное преобразование данных видно целиком.
fn doubled_positives(values: &[i32]) -> Vec<i32> {
    values
        .iter()
        .copied()
        .filter(|value| *value > 0)
        .map(|value| value * 2)
        .collect()
}

// Управление потоком и запись в файл проще проследить по шагам.
fn write_until_stop(lines: &[&str], path: &std::path::Path) -> std::io::Result<()> {
    use std::io::Write;

    let mut file = std::fs::File::create(path)?;
    for &line in lines {
        if line == "STOP" {
            break;
        }
        if line.is_empty() {
            continue;
        }
        writeln!(file, "{line}")?;
    }
    Ok(())
}
```

**Проверка выбора:** если цикл лишь фильтрует/преобразует элементы и собирает результат, попробуй `filter`/`map`/`collect`. Если цепочка требует побочных эффектов, вложенных замыканий и обходных приёмов ради выхода, вернись к явному циклу. Избегай индексного `0..len` для простого обхода элементов и промежуточного `collect`, если коллекция дальше не нужна. Сравни производительность на данных задачи только там, где это имеет значение.

## Времена жизни

Полагайся на правила элизии; указывай явно, только когда компилятор требует или когда возвращаемая ссылка связана лишь с одним из нескольких входов. Не храни ссылки в структурах, чтобы избежать одного `clone()`, — это распространяет параметр времени жизни на всех пользователей структуры. Ограничение `T: 'static` означает «не содержит нестатичных ссылок», а не «живёт вечно».
