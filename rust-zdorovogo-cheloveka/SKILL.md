# Rust здорового человека

Работай как внимательный сопровождающий проекта: сначала пойми контракт, затем внеси минимальную правку и проверь её. Выбирай конструкции по смыслу и требованиям владения, а не по универсальным запретам. Этот файл — порядок работы и самые частые ошибки. Правила выбора по темам и проверенные примеры — в справочниках.

## Справочники

Первый шаг любой задачи: определи по таблице её темы и прочитай соответствующие справочники целиком, до правки кода. Остальные не читай. В отчёте назови прочитанные справочники.

| Файл | Тема задачи |
|------|-------------|
| [ownership.md](references/ownership.md) | `&str` или `String`, срезы вместо `&Vec`/`&String`, `clone()`, цикл или итераторы, времена жизни |
| [errors.md](references/errors.md) | `Result` или паника (`unwrap`, `expect`, индексация), `?` или `match`, тип ошибки, `# Errors`/`# Panics`, переполнение, `as`, размеры и лимиты из внешних данных |
| [api.md](references/api.md) | структура кода и модули, имена и комментарии, `derive`, документация, совместимость, `impl Trait`/`dyn`/`Into`/`Cow`, аргументы-флаги `bool`/`Option`, `match` по enum, трейты и async-методы в них |
| [unsafe-ffi-async.md](references/unsafe-ffi-async.md) | `unsafe`, FFI и `extern "C"`, async: рантайм, блокирующие вызовы, мьютекс через `.await` |

## Перед изменением

1. Сформулируй наблюдаемое поведение и критерий успеха. Отдельно отметь инварианты: публичный интерфейс, форматы данных, типы ошибок и поведение, которое должно сохраниться. Отметь внешние поверхности — публичный API, HTTP и CLI, конфигурацию, serde-форматы — и оцени совместимость ([api.md](references/api.md#совместимость)). Назови существенное допущение; уточни требование, если разные трактовки меняют контракт.
2. В существующем репозитории посмотри `git status --short` до правки. Прочитай корневой и нужный пакетный `Cargo.toml`: `edition`, `rust-version`, зависимости, features и наследование из `[workspace.package]`. Проверь `rust-toolchain.toml`/`rust-toolchain`, наличие `Cargo.lock`, конфигурацию rustfmt/Clippy (`rustfmt.toml`, `clippy.toml`, `[lints]` в манифесте) и относящиеся к пакету команды CI, включая наборы features (`--all-features`, `--no-default-features`).
3. Прочитай ближайший код, вызовы и существующие тесты. Ищи дальше только для выяснения контракта или зависимостей. В новом проекте следуй заданным пользователем ограничениям; не добавляй зависимости или настройку ради гипотетических будущих задач.
4. Определи минимальный список затрагиваемых файлов. Для ошибки по возможности воспроизведи её значимым тестом или сценарием; для рефакторинга проверь важное поведение до правки.
5. Оцени объём. Ориентир: около 500 изменённых строк сложной логики или 800 механических. Это сигнал, а не лимит: если правка выходит больше и делится на независимые части, предложи пользователю этапы по реальным зависимостям и местам вызова и начни с наименьшего цельного.

## При написании кода

- Предпочитай простой код, в котором причина владения, обработки ошибки и ветвления видна читателю. Не создавай абстракцию впрок и не добавляй защиту от невозможного по контракту случая.
- Следуй стилю соседнего кода. Меняй только строки, необходимые для задачи; убери импорты и переменные, ставшие лишними вследствие своей правки. Не обновляй edition, MSRV, зависимости, lockfile или соседние модули «заодно». Не добавляй крейты (`thiserror`, `anyhow` и т. п.) без просьбы пользователя, если их ещё нет в проекте.
- Имя нового крейта и API зависимости не бери по памяти: проверь по `cargo info` и исходникам версии из `Cargo.lock` ([project.md](references/project.md#зависимости)).
- Меняя поведение, обнови документацию в той же правке.

### Частые ошибки

Перед сдачей сверь каждую затронутую строку с этим списком; подробности — в справочниках.

- `clone()` добавлен только ради того, чтобы замолчал borrow checker; `&Vec<T>`/`&String` в параметре вместо `&[T]`/`&str`.
- Ошибка входа, файла или сети превращена в панику (`unwrap`, индексация); исходная ошибка потеряна в `map_err(|e| e.to_string())`; `map_err(|_| …)` и причина, сохранённая строкой в поле, тоже теряют цепочку.
- Число или размер из внешних данных: `as` вместо `try_from`, арифметика без `checked_*`, выделение памяти без лимита.
- `_` в `match` по своему enum; `true`/`None` в вызове, смысл которого не виден без сигнатуры.
- Обобщение (`impl Into`, `dyn`, трейт с одной реализацией, лишний `derive`) без второго реального вызывающего.
- Новый `unsafe` без `// SAFETY:`; блокирующий вызов или guard `std::sync::Mutex` через `.await`.
- Подавление линта через `#[allow]` на модуле вместо `#[expect(…, reason = "…")]` на выражении или функции.
- В правке остались `dbg!`, отладочный `println!`, закомментированный код или `TODO` без задачи.
- Комментарий пересказывает код, а не объясняет «почему»; вложенные `if let`/`match` вместо раннего выхода (`?`, `return`, `let … else`); имена `get_x`, `data`, `info`, `manager` вместо `as_`/`to_`/`into_` и геттера без `get_` ([api.md](references/api.md#структура-и-имена)).
- Отчёт утверждает «вывод прежний», «совместимо с MSRV» или «проверено», хотя этого не запускали; не названы прочитанные справочники.
- Тест без причины сравнивает поля по одному вместо объекта целиком или меняет переменные окружения процесса.

## После изменения

1. Запусти относящийся к задаче тест или сценарий, затем значимые тесты затронутого пакета (`cargo test -p <пакет>`; для библиотек это включает doc-тесты). Используй закреплённые features и toolchain; если CI проверяет несколько наборов features и правка их касается, повтори проверку для них.
2. Если проект заявляет MSRV (`rust-version`), проверь совместимость ([project.md](references/project.md#msrv)); успешная сборка на более новой версии её не доказывает.
3. Форматируй и проверяй только свои файлы (`rustfmt --edition <edition> <файлы>`, `rustfmt --check`); `cargo fmt --all` — только если `git status` до правки был чистым. При уместности — Clippy для затронутого пакета, с `--locked`, если `Cargo.lock` есть и зависимости не меняются ([project.md](references/project.md#сборка-форматирование-и-clippy)). Предупреждения, существовавшие до правки, не выдавай за свои.
4. Просмотри `git status --short`, `git diff --stat`, `git diff` и `git diff --check`. Сравни с начальным состоянием; убедись, что каждая твоя строка относится к задаче и что конфигурация проекта не изменилась случайно. Не стирай чужие незавершённые изменения.
5. Коротко сообщи, что изменено и почему, какие справочники прочитаны, какие команды прошли, что не удалось проверить и по какой причине. Не называй непроведённые проверки успешными.
