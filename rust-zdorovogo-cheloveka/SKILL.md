# Rust здорового человека

Работай как внимательный сопровождающий проекта: сначала пойми контракт, затем внеси минимальную правку и проверь её. Выбирай конструкции по смыслу и требованиям владения, а не по универсальным запретам. Когда затронуты строки, срезы, клонирование, паники, ошибки, сигнатуры, обход коллекций, времена жизни, `unsafe`, async, аргументы-флаги, `match`, трейты, подавление линтов или тесты, сверяйся с разделом «Правила выбора» ниже.

## Перед изменением

1. Сформулируй наблюдаемое поведение и критерий успеха. Отдельно отметь инварианты: публичный интерфейс, форматы данных, типы ошибок и поведение, которое должно сохраниться. Перечисли внешние поверхности, которых касается правка: публичный API крейта, HTTP- и CLI-интерфейс, загрузку конфигурации и переменные окружения, форматы на диске и в сети (serde), — изменение любой из них ломает совместимость. Назови существенное допущение; уточни требование, если разные трактовки меняют контракт.
2. В существующем репозитории посмотри `git status --short` до правки. Прочитай корневой и нужный пакетный `Cargo.toml`: `edition`, `rust-version`, зависимости, features и наследование из `[workspace.package]`. Проверь `rust-toolchain.toml`/`rust-toolchain`, наличие `Cargo.lock`, конфигурацию rustfmt/Clippy (`rustfmt.toml`, `clippy.toml`, `[lints]` в манифесте) и относящиеся к пакету команды CI, включая наборы features (`--all-features`, `--no-default-features`).
3. Прочитай ближайший код, вызовы и существующие тесты. Ищи дальше только для выяснения контракта или зависимостей. В новом проекте следуй заданным пользователем ограничениям; не добавляй зависимости или настройку ради гипотетических будущих задач.
4. Определи минимальный список затрагиваемых файлов. Для ошибки по возможности воспроизведи её значимым тестом или сценарием; для рефакторинга проверь важное поведение до правки.
5. Оцени объём. Правка сложной логики укладывается примерно в 500 изменённых строк, механическая — в 800. Если выходит больше, предложи пользователю этапы по реальным зависимостям и местам вызова и начни с наименьшего цельного.

## При написании кода

- Предпочитай простой код, в котором причина владения, обработки ошибки и ветвления видна читателю. Абстракция, в том числе вспомогательная функция, появляется со вторым применением: код, вызываемый один раз, остаётся на месте вызова. Не добавляй защиту от невозможного по контракту случая.
- Модули по умолчанию приватны; наружу выходит только то, что нужно вызывающим, явным `pub`/`pub use`. Тестовые помощники живут под `#[cfg(test)]` или в `tests/`, а не в API крейта. Целевой размер модуля — до ~500 строк без тестов; новую функциональность для файла длиннее ~800 строк помещай в новый модуль рядом и переноси туда связанные тесты и документацию. Существующий большой файл без задачи не дроби.
- Документация модуля, типа и функции описывает только существующие API и текущее поведение. Меняя поведение, обнови её в той же правке и сверь каждое упомянутое имя с кодом.
- Читай входные данные через `&str` и `&[T]`, если владение не нужно; бери или возвращай `String`/`Vec<T>`, когда данные должны жить независимо. Заимствуй для чтения, перемещай на последнем использовании, клонируй при осознанной потребности во втором владельце или при оправданном упрощении.
- Ошибки входных данных и окружения возвращай как `Result`; паникуй только при нарушении инварианта программы. Применяй `?` для передачи ошибки вызывающей стороне и `match`, когда разные ошибки требуют разных решений. Не теряй исходную ошибку и не превращай её в строку без причины.
- Выбирай итераторы для ясного преобразования данных, явный цикл для последовательных действий и управления потоком.
- Не обобщай сигнатуры заранее: `impl Trait`, `Into`, `AsRef`, `Cow` и `dyn` — по конкретной потребности.
- Не добавляй `unsafe`, явные времена жизни и новые async-зависимости без необходимости; в async-коде следуй рантайму проекта и не блокируй поток.
- Следуй стилю соседнего кода. Меняй только строки, необходимые для задачи; убери импорты и переменные, ставшие лишними вследствие своей правки. Не обновляй edition, MSRV, зависимости, lockfile или соседние модули «заодно». Не добавляй крейты (`thiserror`, `anyhow` и т. п.) без просьбы пользователя, если их ещё нет в проекте.
- Правило, которое умеет проверять компилятор или Clippy, надёжнее закрепить в `[lints]`/`clippy.toml`, чем в тексте. Если такое правило раз за разом нарушается, предложи пользователю линт — это изменение конфигурации проекта, а не часть текущей правки.

## После изменения

1. Запусти относящийся к задаче тест или сценарий, затем значимые тесты затронутого пакета (`cargo test -p <пакет>`; для библиотек это включает doc-тесты). Используй закреплённые features и toolchain; если CI проверяет несколько наборов features и правка их касается, повтори проверку для них.
2. Если проект заявляет MSRV (`rust-version`) и нужный компилятор установлен, проверь совместимость: `cargo +<rust-version> check -p <пакет> --locked`. Успешная сборка на более новой версии совместимости не доказывает; не устанавливай toolchain без согласия пользователя — просто сообщи, что проверка не проведена.
3. Если `Cargo.lock` уже есть и зависимости не меняются, используй `--locked` при Cargo-проверках. Проверь форматирование командой проекта, например `cargo fmt --all -- --check`; при уместности запусти Clippy для затронутого пакета (`cargo clippy -p <пакет> --all-targets`). Не выдавай предупреждения, существовавшие до правки, за результат своей работы и не считай их своими. Форматирование поведения не меняет, поэтому после `cargo fmt` тесты не повторяй; после `cargo clippy --fix` просмотри diff и повтори тесты, если исправление затронуло логику. Cargo может долго ждать блокировку каталога сборки (`Blocking waiting for file lock`) — это нормально, дождись завершения команды.
4. Просмотри `git status --short`, `git diff --stat`, `git diff` и `git diff --check`. Сравни с начальным состоянием; убедись, что каждая твоя строка относится к задаче и что конфигурация проекта не изменилась случайно. Не стирай чужие незавершённые изменения.
5. Коротко сообщи, что изменено и почему, какие команды прошли, что не удалось проверить и по какой причине. Не называй непроведённые проверки успешными.

# Правила выбора

Они описывают причину выбора, а не вводят запрет на одну из конструкций. Сначала проверь контракт функции, владение данными и поведение при ошибке; затем выбери самый ясный вариант, который решает текущую задачу.

## 1. `&str` или `String`

**Принцип:** принимай `&str`, когда функции достаточно прочитать текст во время вызова. Принимай или возвращай `String`, когда результат должен владеть текстом: хранить его после вызова, менять или передать владение дальше. Если функция действительно забирает строку, принимай `String`, чтобы вызывающий код мог передать готовое значение без скрытого клонирования.

```rust
// Только чтение: подойдут и строковый литерал, и String.
fn is_user_name(name: &str) -> bool {
    name.starts_with("user_")
}

// Хранение: User должен владеть именем после завершения вызова.
struct User {
    name: String,
}

impl User {
    fn new(name: String) -> Self {
        Self { name }
    }
}
```

**Проверка выбора:** если заменить `String` в `User` на `&str`, появится зависимость времени жизни `User` от входной строки. Она оправданна, только когда такое заимствование действительно задумано. Если заменить параметр `is_user_name` на `String`, простой вызов начнёт требовать передачи владения или ненужного выделения памяти. При создании нового текста, например после `to_uppercase()`, возвращай `String`; ссылку на локально созданную строку возвращать нельзя.

## 2. Срезы вместо ссылок на владеющие контейнеры

**Принцип:** для чтения принимай `&[T]` вместо `&Vec<T>`, `&str` вместо `&String`, `&T` вместо `&Box<T>`, `&Path` вместо `&PathBuf`. Срез принимает больше вариантов (массив, часть вектора, литерал) и не раскрывает, как вызывающий хранит данные. `&mut Vec<T>` оправдан, только если функция меняет длину (`push`, `retain`); для изменения элементов достаточно `&mut [T]`.

```rust
fn total_len(names: &[String]) -> usize {
    names.iter().map(String::len).sum()
}
```

**Проверка выбора:** если функция вызывает у `&Vec<T>` только методы среза (`iter`, `len`, индексацию), замени тип на `&[T]` — вызовы с `&vec` продолжат компилироваться благодаря deref-приведению. Clippy отмечает это как `ptr_arg`. В публичном API такая замена меняет сигнатуру, поэтому делай её только в рамках задачи.

## 3. `clone()` или заимствование/перемещение

**Принцип:** сначала выясни, кому требуется владение. Заимствуй для временного чтения, перемещай значение, если прежнему владельцу оно больше не нужно. Клонируй осознанно, если нужны два независимых значения или если это делает простой участок кода заметно понятнее и стоимость приемлема. Не добавляй `clone()` лишь затем, чтобы подавить ошибку borrow checker, не разобравшись в причине.

```rust
// После чтения строку можно передать в хранилище без копии.
fn keep_name(name: String, names: &mut Vec<String>) {
    println!("{name}");
    names.push(name);
}

// Оба хранилища должны независимо владеть своим экземпляром строки.
fn keep_in_both(name: String, active: &mut Vec<String>, history: &mut Vec<String>) {
    history.push(name.clone());
    active.push(name);
}
```

**Проверка выбора:** удали `clone()` мысленно: если исходное значение можно передать на последнем использовании, копия лишняя; если оба получателя должны хранить независимые строки, она обоснованна. Учитывай конкретный тип: `String::clone()` копирует содержимое, а `Arc::clone()` создаёт ещё один указатель на те же данные с увеличением счётчика ссылок; `Clone` сам по себе не обещает ни дешёвую, ни глубокую копию. Не усложняй архитектуру только ради устранения одной дешёвой и понятной копии.

## 4. `Result` или паника (`unwrap`, `expect`, `panic!`, индексация)

**Принцип:** ошибка, которую может вызвать вход, файл, сеть или пользователь, — это `Result` или `Option`. Паника допустима, когда случившееся означает баг в программе: нарушен инвариант, который код гарантирует сам. В таком случае предпочитай `expect` с сообщением о том, *почему* значение должно быть, а не о том, что пошло не так. Индексация `v[i]`, деление на ноль и `unwrap` паникуют так же, как `panic!`, — оценивай их по тому же правилу.

```rust
// Пустой срез — нормальный случай, а не баг: возвращаем Option.
fn middle(values: &[i32]) -> Option<i32> {
    values.get(values.len() / 2).copied()
}

// Непустота проверена строкой выше; expect фиксирует инвариант.
fn first_char(word: &str) -> char {
    assert!(!word.is_empty(), "word must be non-empty");
    word.chars().next().expect("строка непуста: проверено выше")
}
```

**Проверка выбора:** спроси, может ли `None`/`Err` здесь возникнуть при корректной программе и некорректных внешних данных. Если да — паника недопустима, верни ошибку. Если нет — `expect` с объяснением инварианта. В тестах, примерах и прототипах по просьбе пользователя `unwrap` уместен. Публичная функция библиотеки, которая может паниковать, документирует это в разделе `# Panics`. Не заменяй `unwrap` на `unwrap_or_default()` молча: это меняет поведение, а не только стиль. Если ошибку нельзя вернуть наверх и нужно поведение по умолчанию, выбирай его по последствиям: проверка доступа, путь к файлу, подпись, лимит — отказ (fail-closed); отображение, логирование, диагностика — продолжение с запасным значением и записью в лог (fail-open).

## 5. `?` или `match`

**Принцип:** используй `?`, когда текущая функция должна прекратить работу и передать ошибку вызывающей стороне. Используй `match` (или `if let`/комбинаторы), когда нужно принять решение по конкретной ошибке: выбрать запасной путь, повторить операцию, преобразовать значение или выполнить разное действие для разных случаев. При `?` ошибка может преобразовываться через `From`; это должно соответствовать контракту возвращаемого типа.

```rust
// Ошибку чтения обрабатывает вызывающая сторона.
fn line_count(path: &str) -> std::io::Result<usize> {
    let text = std::fs::read_to_string(path)?;
    Ok(text.lines().count())
}

// Отсутствие файла — отдельный допустимый случай, остальные ошибки передаются выше.
fn read_or_empty(path: &str) -> std::io::Result<String> {
    match std::fs::read_to_string(path) {
        Ok(text) => Ok(text),
        Err(error) if error.kind() == std::io::ErrorKind::NotFound => Ok(String::new()),
        Err(error) => Err(error),
    }
}
```

**Проверка выбора:** если все ветви `match` только передают `Err` наверх, попробуй `?` и убери шаблонный код. Если `?` скрывает важное для задачи различие между ошибками, явно обработай его. Не вставляй `?` там, где функция возвращает `()` или несовместимый с ошибкой тип. Не пиши `Ok(operation()?)`, когда тип ошибки совпадает и можно вернуть `operation()` напрямую; если нужно преобразование через `From`, эта форма оправданна (см. пример в п. 6).

## 6. Какой тип ошибки

**Принцип:** сначала следуй тому, что уже принято в проекте. Библиотека обычно возвращает собственный тип ошибки (enum), чтобы вызывающий мог сопоставить варианты и получить исходную причину через `source()`. Приложение (бинарник) может собирать ошибки в `Box<dyn std::error::Error>` или `anyhow::Error`, если он уже в зависимостях, добавляя контекст там, где он помогает понять сбой. `thiserror` лишь генерирует тот же код, что и ручная реализация, — не добавляй его ради одной правки.

```rust
#[derive(Debug)]
enum ConfigError {
    Read(std::io::Error),
    Port(std::num::ParseIntError),
}

impl std::fmt::Display for ConfigError {
    fn fmt(&self, f: &mut std::fmt::Formatter<'_>) -> std::fmt::Result {
        match self {
            Self::Read(_) => write!(f, "не удалось прочитать конфигурацию"),
            Self::Port(_) => write!(f, "некорректный номер порта"),
        }
    }
}

impl std::error::Error for ConfigError {
    fn source(&self) -> Option<&(dyn std::error::Error + 'static)> {
        match self {
            Self::Read(error) => Some(error),
            Self::Port(error) => Some(error),
        }
    }
}

impl From<std::io::Error> for ConfigError {
    fn from(error: std::io::Error) -> Self {
        Self::Read(error)
    }
}

impl From<std::num::ParseIntError> for ConfigError {
    fn from(error: std::num::ParseIntError) -> Self {
        Self::Port(error)
    }
}

// `Ok(...?)` здесь нужен: `?` преобразует ParseIntError в ConfigError.
fn read_port(path: &std::path::Path) -> Result<u16, ConfigError> {
    let text = std::fs::read_to_string(path)?;
    Ok(text.trim().parse()?)
}
```

**Проверка выбора:** может ли вызывающий по-разному реагировать на разные сбои? Если да — нужны различимые варианты, а не строка. `map_err(|e| e.to_string())` теряет тип и цепочку причин — используй только на границе, где ошибка превращается в сообщение для человека. `Display` описывает текущий уровень и не дублирует текст `source()`, иначе при выводе цепочки сообщение повторится. Добавление варианта в публичный enum ошибок — несовместимое изменение, если enum не помечен `#[non_exhaustive]`.

## 7. Цикл или цепочка итераторов

**Принцип:** применяй итераторы, если последовательность преобразований читается как описание результата. Пиши явный `for`, когда в теле несколько действий, побочные эффекты, `break`/`continue` или ранняя передача ошибки и цепочка методов затрудняет понимание. Цикл `for` тоже работает через итератор; выбирать между ними по одному лишь предположению о скорости не следует.

```rust
// Линейное преобразование данных видно целиком.
fn doubled_positives(values: &[i32]) -> Vec<i32> {
    values
        .iter()
        .copied()
        .filter(|value| *value > 0)
        .map(|value| value * 2)
        .collect()
}

// Управление потоком и запись в файл проще проследить по шагам.
fn write_until_stop(lines: &[&str], path: &std::path::Path) -> std::io::Result<()> {
    use std::io::Write;

    let mut file = std::fs::File::create(path)?;
    for &line in lines {
        if line == "STOP" {
            break;
        }
        if line.is_empty() {
            continue;
        }
        writeln!(file, "{line}")?;
    }
    Ok(())
}
```

**Проверка выбора:** если цикл лишь фильтрует/преобразует элементы и собирает результат, попробуй `filter`/`map`/`collect`. Если цепочка требует побочных эффектов, вложенных замыканий и обходных приёмов ради выхода, вернись к явному циклу. Избегай индексного `0..len` для простого обхода элементов и промежуточного `collect`, если коллекция дальше не нужна. Сравни производительность на данных задачи только там, где это имеет значение.

## 8. Гибкие сигнатуры: `impl Trait`, `dyn`, `Into`, `Cow`

**Принцип:** по умолчанию пиши конкретные типы (`&str`, `&[T]`, `String`). Обобщай, когда есть реальная потребность:

- `impl Into<String>` — в публичном конструкторе, который хранит строку, если вызывающие часто передают литералы; во внутреннем коде проще `String`.
- `impl AsRef<Path>` — для путей в публичном API по образцу `std::fs`; внутри одной функции достаточно `&Path`.
- `Cow<'_, str>` — когда функция обычно возвращает вход без изменений и лишь иногда создаёт новую строку, а выделение памяти на горячем пути заметно.
- Обобщение (`<S: Shape>`, `impl Shape`) — когда на одном вызове один тип и важна статическая диспетчеризация; `dyn Trait` — когда в одной коллекции разные типы или нужно ограничить размер кода и время компиляции.

```rust
use std::borrow::Cow;

fn tabs_to_spaces(text: &str) -> Cow<'_, str> {
    if text.contains('\t') {
        Cow::Owned(text.replace('\t', "    "))
    } else {
        Cow::Borrowed(text)
    }
}

trait Shape {
    fn area(&self) -> f64;
}

// Все элементы одного типа.
fn largest_area<S: Shape>(shapes: &[S]) -> f64 {
    shapes.iter().map(Shape::area).fold(0.0, f64::max)
}

// В коллекции разные фигуры.
fn total_area(shapes: &[Box<dyn Shape>]) -> f64 {
    shapes.iter().map(|shape| shape.area()).sum()
}
```

**Проверка выбора:** назови второго реального вызывающего, которому обобщение помогает. Если его нет — оставь конкретный тип. Каждый обобщённый параметр усложняет сообщения компилятора и документацию.

## 9. Времена жизни, `unsafe`, async

**Времена жизни.** Полагайся на правила элизии; указывай явно, только когда компилятор требует или когда возвращаемая ссылка связана лишь с одним из нескольких входов. Не храни ссылки в структурах, чтобы избежать одного `clone()`, — это распространяет параметр времени жизни на всех пользователей структуры. Ограничение `T: 'static` означает «не содержит нестатичных ссылок», а не «живёт вечно».

**`unsafe`.** Не вводи его без явной необходимости (FFI, доказанная измерением потребность в производительности, отсутствие безопасной альтернативы) и согласия пользователя. Каждый `unsafe`-блок сопровождай комментарием `// SAFETY:` о том, какие условия выполняются и почему; у `unsafe fn` — раздел `# Safety` в документации. Правя существующий `unsafe`-код, сохрани его инварианты и перечитай комментарии. Если проект использует Miri, прогони затронутые тесты через `cargo +nightly miri test`.

**Async.** Используй рантайм и примитивы, уже выбранные в проекте; не смешивай рантаймы. Не вызывай блокирующие операции (`std::fs`, `std::thread::sleep`, тяжёлые вычисления) внутри async-функций — используй асинхронные аналоги рантайма или вынос в `spawn_blocking`. Не держи guard от `std::sync::Mutex` через `.await` (Clippy: `await_holding_lock`); сократи область блокировки или используй асинхронный мьютекс, если блокировка действительно должна пережить `.await`.

## 10. Аргументы-флаги: `bool` и `Option`

**Принцип:** вызов читается без заглядывания в сигнатуру. Если по месту вызова `open(path, true)` или `connect(addr, None)` не видно, что означает литерал, выбери форму API, которая называет смысл: enum из двух вариантов, отдельные именованные методы, newtype или структуру параметров. Исключение — единственный аргумент метода, чьё имя совпадает с именем параметра: `.enabled(false)` уже понятен.

```rust
enum Overwrite {
    Allow,
    Refuse,
}

fn save(path: &std::path::Path, data: &[u8], overwrite: Overwrite) -> std::io::Result<()> {
    let mut options = std::fs::OpenOptions::new();
    match overwrite {
        Overwrite::Allow => options.write(true).create(true).truncate(true),
        Overwrite::Refuse => options.write(true).create_new(true),
    };
    std::io::Write::write_all(&mut options.open(path)?, data)
}

// Вызов объясняет себя: save(path, data, Overwrite::Refuse)
```

**Проверка выбора:** прочитай вызов вслух без сигнатуры. Если непонятно, что значат `true`, `None` или число, а сигнатуру менять нельзя (чужой API, публичный интерфейс вне задачи), поставь перед литералом комментарий с точным именем параметра: `connect(addr, /*timeout*/ None)`. Строковые и символьные литералы обычно понятны сами. Меняй сигнатуру существующей функции только в рамках задачи.

## 11. `match`: перечисляй варианты

**Принцип:** в `match` по своему enum перечисляй варианты явно, без `_`. Тогда добавление варианта даёт ошибку компиляции в каждом месте, где его нужно обработать, а не молча уходит в ветку по умолчанию. Если несколько вариантов обрабатываются одинаково, объединяй их через `|`.

```rust
enum Stage {
    Queued,
    Running,
    Paused,
    Done,
}

fn is_active(stage: &Stage) -> bool {
    match stage {
        Stage::Running | Stage::Paused => true,
        Stage::Queued | Stage::Done => false,
    }
}
```

**Проверка выбора:** если бы в enum появился вариант `Failed`, заметил бы это `match`? Если нет — замени `_` на перечисление. `_` оправдан для чужого `#[non_exhaustive]` enum (там он обязателен), для enum с множеством вариантов, из которых важны единицы, и для значений, а не вариантов (числа, строки). Clippy: `match_wildcard_for_single_variants`, `wildcard_enum_match_arm`.

## 12. Трейты: документация и async

**Принцип:** у нового трейта есть doc-комментарий: какую роль он играет, кто его вызывает и что обязана гарантировать реализация (потокобезопасность, идемпотентность, поведение при ошибке). Трейт — контракт между несколькими реализациями, и без описания каждая реализация угадывает его заново.

Для асинхронного метода трейта опиши будущее явно: `fn f(&self) -> impl Future<Output = T> + Send;` (Rust 1.75+). Так требование `Send` видно в контракте и проверяется для каждой реализации, а сама реализация может оставаться `async fn`. `#[async_trait]` и `#[allow(async_fn_in_trait)]` в новых трейтах не нужны; существующий трейт на `#[async_trait]` не переделывай без задачи.

```rust
use std::future::Future;

/// Хранилище кусков торрента.
///
/// Вызывается из задач tokio на разных потоках, поэтому будущие обязаны быть `Send`.
/// `read` для куска, который ещё не записан, возвращает `Ok(None)`, а не ошибку.
trait PieceStore {
    fn read(&self, index: u32) -> impl Future<Output = std::io::Result<Option<Vec<u8>>>> + Send;
}

struct MemoryStore;

impl PieceStore for MemoryStore {
    async fn read(&self, _index: u32) -> std::io::Result<Option<Vec<u8>>> {
        Ok(None)
    }
}
```

**Проверка выбора:** если трейт нужен как `dyn Trait`, методы с `impl Future` не объектно-безопасны — тогда верни `Pin<Box<dyn Future<Output = T> + Send + '_>>` или оставь уже принятое в проекте решение.

## 13. Подавление линтов

**Принцип:** подавляй линт на самом узком участке (выражение, функция, а не модуль) атрибутом `#[expect(lint, reason = "...")]` (Rust 1.81+). В отличие от `#[allow]`, `expect` сам предупредит, когда подавление станет лишним, а `reason` объясняет читателю, почему правило здесь не действует.

```rust
#[expect(clippy::cast_possible_truncation, reason = "бокс собирается из заголовков и меньше 4 ГиБ")]
fn box_len(body: &[u8]) -> u32 {
    (body.len() + 8) as u32
}
```

**Проверка выбора:** сначала попробуй исправить код так, чтобы линт не срабатывал; подавление — для случаев, когда линт ошибается или правило здесь неприменимо. Если `rust-version` проекта ниже 1.81, используй `#[allow(...)]` с комментарием о причине. Предупреждение компилятора — тоже сигнал: исправь причину, а не подавляй её.

## 14. Тесты

**Принцип:** тест проверяет наблюдаемое поведение и падает с понятным сообщением.

- Сравнивай объект целиком: `assert_eq!(parsed, Config { port: 8080, host: "localhost".into() })`, а не поле за полем. Так новое поле не выпадет из проверки, а diff в сообщении покажет всё расхождение. Если тип не реализует `PartialEq` и `Debug`, добавь `derive`, когда это естественно для типа; публичному типу — с учётом того, что это расширяет его API.
- Проверяй поведение, которое может сломаться: не тестируй значения констант и статические таблицы, а для удалённой логики не пиши тест на её отсутствие.
- Передавай зависимости от окружения параметром. Тесты работают параллельно в потоках одного процесса, поэтому изменение переменных окружения в одном тесте влияет на соседние; в edition 2024 `std::env::set_var` и `remove_var` к тому же `unsafe`. Читай окружение на границе программы и передавай значение в тестируемую функцию.
- Тестовые помощники держи в тестовом модуле или в `tests/`; основная реализация не получает функций «только для тестов». Перед тем как написать помощник, проверь, нет ли готового в проекте.

```rust
#[derive(Debug, PartialEq)]
struct Config {
    port: u16,
    host: String,
}

fn parse_config(text: &str) -> Option<Config> {
    let (host, port) = text.split_once(':')?;
    Some(Config { port: port.parse().ok()?, host: host.to_owned() })
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn parses_host_and_port() {
        assert_eq!(
            parse_config("localhost:8080"),
            Some(Config { port: 8080, host: "localhost".to_owned() })
        );
    }
}
```

**Проверка выбора:** удали мысленно проверяемую строку кода — упадёт ли тест? Если нет, он проверяет не то. Добавь поле в структуру — заметит ли тест, что его значение неверно? Если нет, сравни объект целиком.
