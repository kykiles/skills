# Испытания rust-zdorovogo-cheloveka

Стенд для проверки, как модель решает типичные Rust-задачи со скиллом и без него. Каталог не входит в устанавливаемый скилл.

## Кейсы

| Кейс | Задача исполнителю | Что ловит оценщик |
|------|--------------------|-------------------|
| `r01-errors` | Сервис падает с паникой на конфиге с опечаткой в значении | паника на внешних данных; исходная ошибка (`ParseIntError`, `ParseBoolError`) должна остаться в цепочке `source()`; ошибка, превращённая в строку; `Display`, который повторяет текст `source()` (сообщение в выводе дважды); молчаливая подмена значением по умолчанию |
| `r02-limits` | Парсер бинарного архива падает, съедает память или отдаёт не те байты на присланных файлах | `as u32` с усечением 64-битного смещения вместо `try_from`; переполнение `offset + len`; `Vec::with_capacity` по `count` из заголовка без лимита (аллокатор теста отказывает в запросах больше 64 МиБ); лимит 65 536 записей из задачи |
| `r03-enum` | Добавить статус заказа `Returned` и поддержать его везде | `_`/`matches!`, которые молча проглатывают новый вариант: `from_code`, `is_open`, `can_move`, `refund`, список `Status::ALL` в сводке, CLI |
| `r04-refactor` | Отрефакторить длинную функцию без изменения вывода | вывод байт в байт (3000 случайных входов против исходной реализации); `Cargo.toml` с `rust-version = "1.74"` и `Cargo.lock` не изменены; API новее MSRV (`incompatible_msrv`); незакоммиченные правки коллеги и его неотформатированный файл; публичные элементы (`cargo doc`) и сигнатуры |
| `r05-holdout` | Статистика по логу медленная и занимает памяти больше самого лога | число выделений памяти и пик памяти не растут с размером лога (считающий аллокатор); результат и сигнатуры прежние; порядок при равенстве |

`r05-holdout` — отложенный кейс: написан последним, его тема (владение, `clone()`, промежуточные `collect`) не пересекается с `r01`–`r04`. Он показывает перенос правил скилла на новую задачу.

Структура кейса:

- `task.md` — запрос, который получает исполнитель;
- `project/` — исходный проект: только стандартная библиотека, `Cargo.lock` без зависимостей, `edition = "2021"`, `rust-version = "1.74"`;
- `dirty/` — незакоммиченные правки, которые исполнитель застаёт в рабочем дереве;
- `grader/` — скрытые тесты оценщика (`tests/zz_grader*.rs`, интеграционные тесты: видят только публичный API);
- `reference/` — эталонное исправление (только изменённые файлы);
- `broken/*/` — заведомо неверные решения, которые оценщик обязан отклонить; в каждом кейсе есть хотя бы одно правдоподобное;
- `case.env` — настройки кейса: `ORIGINAL_PASSES=1` (исходник корректен), `API_STABLE=1` (сравнить публичные элементы).

## Скрипты

```sh
./prepare.sh r02-limits /tmp/ws/r02   # рабочая копия: git-репозиторий + dirty/
./grade.sh   r02-limits /tmp/ws/r02   # оценка; рабочая копия не меняется
./verify.sh                           # самопроверка стенда
./summarize.py                        # сводные таблицы по results/
./check-examples.py                   # clippy -W pedantic и тесты всех примеров скилла
```

Все команды Cargo идут с `--offline --locked`: сеть не нужна. Нужен stable Rust с `clippy`, `rustfmt` и `rustdoc`; стенд проверен на Rust 1.97.

`grade.sh` работает на копии рабочего каталога, `CARGO_TARGET_DIR` — во временном каталоге. Проверки PASS/FAIL:

- не изменены `Cargo.toml`, `Cargo.lock`, `.gitignore` и файлы из `dirty/`;
- исполнитель не оставил посторонних файлов: новыми могут быть только `.rs`;
- `cargo fmt --check` для изменённых и новых `.rs`-файлов исполнителя (чужой неотформатированный файл не в счёт);
- `cargo build --all-targets` и `cargo clippy --all-targets -- -D warnings`; Clippy по умолчанию включает `incompatible_msrv` и сверяет API std с `rust-version`;
- при `API_STABLE` — список публичных элементов из `cargo doc` совпадает с исходным;
- скрытые тесты `grader/` вместе с тестами проекта (`cargo test`, таймаут 600 с).

Итог — строка `RESULT PASS` или `RESULT FAIL (<число провалов>)`.

Строки `METRIC` на PASS/FAIL не влияют и нужны для оценки «человечности» правки:

| Метрика | Что считает |
|---------|-------------|
| `pedantic_new` | новые предупреждения `clippy::pedantic` относительно исходника (файл + текст, без номера строки); сами предупреждения — в строках `info pedantic:` |
| `dbg` | `dbg!` в добавленных строках |
| `println_outside_main` | `println!` в добавленных строках вне `src/main.rs` и `src/bin/` |
| `todo` | `TODO`/`FIXME` в добавленных строках |
| `unwrap_outside_tests` | `.unwrap()`/`.expect(` в добавленных строках вне тестов |
| `int_as` | `as <целый тип>` в добавленных строках вне тестов (тип источника не известен, считаются все приведения к целым) |
| `clone` | `.clone()` в добавленных строках вне тестов |
| `added`, `removed` | размер правки в строках относительно исходного состояния (коммит + `dirty/`) |
| `size_vs_reference` | `(added + removed)` правки к тому же у эталона |

Тестами для метрик считаются `tests/`, `benches/`, `examples/` и элементы под `#[cfg(test)]`. Подсчёт идёт по тексту строк, без разбора Rust, поэтому метрики — ориентир для ревью, а не оценка.

`verify.sh` требует, чтобы эталон проходил, а исходный код (кроме `r04-refactor`) и все `broken/*` проваливались. С `VERBOSE=1` печатает полный `grade.log` каждой проверки.

## Протокол прогона

1. Для каждого прогона — отдельная рабочая копия `prepare.sh` вне этого репозитория.
2. Исполнитель — свежий субагент (Haiku 4.5) без доступа к плану, оценщику и эталону. Промпт:

   ```text
   Ты работаешь в Rust-проекте в каталоге <WS>. Работай только в этом каталоге и не открывай другие каталоги на диске.
   Сеть недоступна: запускай cargo с --offline.
   [Со скиллом: Сначала прочитай <SKILL>/SKILL.md и нужные ему справочники и следуй им.]
   Не делай git commit.

   Задача от пользователя:
   <содержимое task.md>

   В конце кратко отчитайся: что изменено, какие проверки запущены и с каким результатом.
   ```

3. Условия «без скилла» (`base`) и «со скиллом» (`skill-v1`, затем `skill-v2`…) отличаются только строкой про скилл: модель, промпт и инструменты одинаковые.
4. По 3 прогона на кейс и условие.
5. После прогона: `grade.sh`, `git diff` относительно исходного состояния, ручная оценка по чек-листу ниже.

Результаты лежат в `results/<base|skill-v1>/<кейс>-<n>/`:

- `grade.log` — вывод `grade.sh`;
- `diff.patch` — правка относительно исходного состояния (коммит + `dirty/`);
- `report.md` — итоговый отчёт исполнителя.

### Чек-лист ручной оценки diff

1. **Комментарии.** Объясняют «почему» и инварианты, а не пересказывают код? Не остались ли закомментированный код и отладочные строки?
2. **Имена.** Говорят ли имена о смысле (`max_entries`, а не `data`, `info`, `helper`); соблюдены ли `as_`/`to_`/`into_` и геттеры без `get_`?
3. **Лишняя сложность.** Нет ли трейта с одной реализацией, нового типа ошибки или помощника там, где хватило бы строки; правок «заодно» вне задачи?
4. **Минимальность.** Каждая строка diff относится к задаче? Чужие правки и конфигурация проекта не тронуты?
5. **Честность отчёта.** Названы ли все изменённые файлы и запущенные команды; не выдана ли непроведённая проверка за успешную; сказано ли, что не проверено (например, MSRV без установленного 1.74)?

## Ограничения

- Совместимость с `rust-version = "1.74"` проверяется только Clippy (`incompatible_msrv`): он ловит API std новее MSRV, но не языковые конструкции. Сборки на Rust 1.74 нет.
- Публичные элементы сравниваются по списку `all.html` из `cargo doc`, а сигнатуры — приведением функций к типу `fn(...)` в скрытых тестах. Изменения полей и методов типов, которые тесты не используют, не ловятся.
- `r02-limits`: выделение больше 64 МиБ аварийно завершает тестовый процесс (`memory allocation of N bytes failed`), остальные тесты этого файла в логе не видны.
- `r05-holdout`: пороги (меньше 1000 выделений и 512 КиБ пика на 100 000 строк) подобраны с запасом относительно эталона и выбраны так, чтобы отклонять копирование каждой строки и сбор всех строк в вектор.
- Исполнитель технически может прочитать файлы вне рабочей копии, поэтому промпт это запрещает, а трассы просматриваются.
- Скилл загружается явной строкой в промпте, поэтому автоматическое срабатывание по `description` здесь не проверяется.
